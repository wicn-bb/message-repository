# 5000 亿 Token 之后：Agent 规模化之前先建立可判定的 Oracle

- 收录日期：2026-10-23
- 原文日期：2026-10-09
- 作者：Maurice Heumann
- 来源：Maurice's Blog（个人开发者实践）
- 原文：[500+ Billion Tokens Later: Letting AI Agents Decompile A First-Person Shooter](https://momo5502.com/posts/2026-10-09-game-decompilation/)
- 主题：AI 提效、代码重构、Agent 编排、自动验证、上下文管理

## 核心观点

多个 Agent 最初很快完成约 80% 的游戏反编译，程序能够启动并加载地图，但大量函数的语义并不正确。人工或 Agent Reviewer 还可能被代码注释中的合理解释说服，把错误实现当成可接受偏差。

转折点是建立字节级比对 Oracle：用原始编译器重建函数，并将目标文件与原始二进制逐字节比较。Agent 得到明确的 `PASS/FAIL`，而不是依赖另一个模型主观审查。项目最终报告 99% 的函数已重建、83% 达到字节完全匹配。

## 值得保留的工程启示

1. 没有机器可判定的验收标准，更多并发 Agent 只会更快地产生难以验证的代码。
2. 验证器必须放在 Agent 无法修改的信任边界外；作者使用 CI 中保存的哈希防止 Agent 绕过检查。
3. Reviewer Agent 会受到待审代码和注释的上下文影响，不能自然地充当独立裁判。
4. 长任务中需要定期刷新核心约束，避免规则在上下文压缩和多轮执行后逐渐失效。
5. 生成代码已经很便宜；当基础假设错误时，删除重来可能比持续修补更经济。

## 提效公式

```text
清晰目标 × 可执行环境 × 机器可判定验收 × 自动反馈循环
```

比单纯依赖“更强模型 × 更多 Agent”更接近长期自治任务的真实约束。

## 证据与限制

这是持续约三个月的一手实践，公开了失败过程、验证方法和最终指标。但代码未公开，游戏名称在原文中未说明，Token 总量因虚拟机日志丢失只能估算为 6000 亿至 7000 亿，因此无法独立复现或审计全部数字。

## 收录理由

这是少见的长期、多 Agent、高失败成本案例。它把 AI 编码的核心问题从“模型能写多少”转向“系统如何客观判断正确”，对代码重构、迁移和大规模自动修复都有直接价值。
