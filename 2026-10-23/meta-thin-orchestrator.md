# 薄编排器：确定性控制与概率性推理应当分层

- 收录日期：2026-10-23
- 原文日期：2026-10-19
- 来源：Engineering at Meta
- 原文：[The Thin Orchestrator: How We Made Our AI Agents More Reliable by Giving the Router Less to Do](https://engineering.fb.com/2026/10/19/ml-applications/thin-orchestrator-ai-agent-architecture/)
- 主题：系统架构、Agent 编排、多 Agent、上下文隔离

## 核心观点

Meta 最初将多套领域知识、配置规则和工作流全部交给一个大 Agent，生产中却出现概念串扰：模型会把一个子系统的字段规则错误套到另一个子系统。

团队后来建立约 1,300 行的薄编排器，将 20 多个工作流路由给 14 个专用 Agent。编排器只负责意图分类、字段收集、去重、可靠性门禁、执行顺序和错误处理；领域推理则在隔离上下文中的专用 Agent 内完成。

## 架构边界

```text
编排层：状态机、权限、重试、校验、路由
Agent 层：领域推理、生成、诊断
知识层：按任务加载，不把全部知识常驻主上下文
```

## 值得保留的工程启示

1. 确定性决策尽量保留为普通程序逻辑，不必让 LLM 再“思考”一次。
2. 专用 Agent 应采用一致结构：知识来源、必需输入、执行步骤、发现规则和故障处理。
3. 新场景优先组合已有 Agent 的工作流模板，而不是继续增加高度耦合的新 Agent。
4. 知识文件在执行时按需加载，减少上下文干扰，并允许知识更新独立于编排器部署。
5. 将失败限制在专用 Agent 内，由编排层负责重试、升级和状态恢复。

## 证据与限制

Meta 报告新数据列的配置准备由人工三至四天缩短到一小时以内，约三分之二的变更无需重大人工修改。数据来自 Meta 内部系统，没有公开完整评测集；文章还引用外部多 Agent 研究佐证上下文隔离，但不能据此证明该架构适用于所有任务。

## 收录理由

文章给出了非常清晰的确定性／概率性边界。对于企业工作流、内部平台和复杂代码库，薄编排器比“一个拥有全部知识的超级 Agent”更容易测试、治理和定位故障。
